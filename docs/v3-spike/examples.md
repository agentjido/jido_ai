# Example catalog

This is the migration planning catalog. For implemented capabilities and their
limits, use the [checked example summary](../../examples/README.md#what-the-examples-can-do)
and [current maturity report](status.md). The proposed families below are not
a claim that every planned feature is supported.

Status: the checked source and test catalog lives in
[examples](../../examples/README.md). The IDs below map to matching source,
guide, and test folders in the root project.

The [unified DSL plan](agent-dsl.md) proposes a small combined authoring example:
one model role, an Action tool, a Flow tool, an operation control, and a typed
result. It draws from `01` through `04`. The full sketch maps its other concepts
to this catalog and keeps new tool adapters separate from current feature parity.

Each example must add a specific behavior. A different prompt or business
domain is not enough to justify another example. Test the real Jido Agent,
Flow, tools, and commit boundary with controlled model responses. Use the
current AI test helpers as the starting point for those controls.

The [public API map](public-api-map.md) defines the call-surface checks for
these examples. Preserve direct versus Agent results and the functions actually
generated by each macro. API cases and historical cases can share one test;
neither requires a second set of application examples.

The [release-history audit](history-audit.md) supplies 22 historical scenario
families and named test variants. All 126 commits in the pinned range now have
source reviews. The historical scenarios are requirements inside this catalog;
they are not 22 extra top-level examples. Link each implemented test to its
stable `history_case` ID and contributing commits.

## Implementation priorities

More executable acceptance cases are required. The current 18 catalog families
are sufficient for planning; do not add more top-level families for the same
behavior. Extend the five working examples and the pending AI authoring example.
Add the runtime examples when their production feature work starts.

Before kickoff, define the expected inputs, outputs, failures, and ownership
rules. Tests for unavailable features can remain pending. Implement each case
with its feature so that the isolated project does not grow into a second AI
framework. The priorities below are part of the goal, not completed tests.

The current tool example uses Map, but it does not hold both tool workers or
force reversed completion. The current streaming example proves live cancellation,
but it does not test a provider stream that ends after a partial answer. These
are distinct acceptance gaps, not claims that a production bug was reproduced.

Extend the one mock server only when a case needs new provider behavior. Useful
next controls are configurable usage on every response, explicit terminal stream
errors/disconnects, and barriers between model rounds. Keep real tool execution
outside the mock. Use the current raw-envelope support where it is sufficient.

History also requires coverage beyond the current Chat Completions mock: preserve
Responses continuation/WebSocket session ownership and generated-media content.
Extend the same server and script contract during those ports. The first
history-derived additions are rich aliases, open tool schemas, binary tool
results, Agent-only key aliases, repair-time credentials, nested structured
output, request/event correlation and portable streamed checkpoints.

## First six examples

### 01 — One typed answer

A support Agent answers a question with no tools. Show direct AI use, a plain
Jido Action/Flow route, and the proposed `agent do` form.

- Record the exact model request and selected model.
- Validate input before the provider call and output before state commit.
- Preserve unrelated domain fields and the prior state after failure.
- Prove model aliases, explicit model selection, retryable fallback, and a
  terminal provider error. Treat fallback as AI policy, not a Flow guarantee.
- Give the three authoring forms the same result and error contract.

Core source: `03_01_model_response`.

### 02 — Structured extraction with bounded repair

Extract a typed support ticket. The first response is invalid; a second response
uses the validation feedback and succeeds.

- Cover static Zoi and supported imported JSON schemas.
- Valid first output makes no repair call. Exhaustion makes exactly the allowed
  calls and preserves prior Agent state.
- Validate the returned content, not only the prompt or provider schema option.
- Keep output-schema checks separate from Agent-state schema checks.
- Preserve multimodal input and uploaded file references as variants.

Core source: `03_07_output_repair`; AI sources: `Output`, `Query`, `GenerateObject`.

### 03 — An approved tool changes the next model input

A model selects an inventory lookup tool. The next model call uses its result.
A second tool requests a permitted domain change.

- Resolve names through a trusted Action registry. Reject unknown names and
  invalid arguments before the tool effect.
- Preserve tool call IDs and canonical success/error envelopes.
- A request can narrow the tool set. Define when explicit per-request tool
  replacement is permitted. Model output cannot expand that permission.
- Run interception before validation and once after final retry completion.
  Preserve the existing restriction on tool name, ID, and Action identity.
- Show how a permitted state change reaches the next tool round and the final
  complete candidate state without StateOps.
- A later failure preserves committed Agent state but does not undo recorded
  external tool work. State the retry and idempotency rule.

Core source: `03_03_tool_call`.

### 04 — A ReAct Flow with parallel tools

The model requests two independent tools, reads both results, then answers.

- Use Flow Map/Join and a bounded loop or executable continuation.
- Hold both workers until both start. Reverse completion order and verify
  call-ID order in the next model input.
- Reject a malformed batch before fan-out if complete batch admission is the
  selected policy. Cover duplicate IDs, empty tools, and one failed item.
- Test model-round limits separately from Exec continuation and time limits.
- Cancel blocked work and check worker cleanup. A later request must work.
- Preserve one terminal commit for this example. Intermediate progress is not
  committed conversation history.

Core sources: `03_04_tool_loop`, `03_05_parallel_tools`.

### 05 — A live request with streaming and steering

A caller starts a request, receives events, adds an instruction during a blocked
model call, and waits for the result.

- Prove actual admission before returning an accepted request handle.
- Keep request IDs, run IDs, and event order. Deliver one terminal event.
- Preserve the current ReAct busy-rejection rule unless an explicit API change
  is selected. Multiple handles do not imply simultaneous runs on one Agent.
- `steer` and `inject` do not create another request. Reject a stale expected
  request ID. Show when queued input enters the next model request.
- Preserve bounded FIFO input, idle rejection and visible user role. An enqueue
  acknowledgement does not prove consumption or persistence. Test both orders
  of enqueue versus atomic closure, including closure before output repair.
- Fail on queue loss instead of treating it as empty. Drop undrained input on
  termination; preserve hard limits even when input is waiting. Run HIST-21
  through each public helper and verify cleanup before a later request.
- Keep caller wait timeout, request cancellation, and execution deadline
  distinct. Cancellation must not affect the next request.
- Cover dead stream sinks, stopped consumers, late events, and cleanup.
- Distinguish failed transport after partial text from a complete provider
  response with accepted non-empty partial content. Preserve the finish reason.
- Deliver early tool activity before a held argument stream completes. Test
  unnamed argument fragments and public delta sequence/correlation separately.
- Compare one active Flow plus a runtime input channel with several short
  Turns. Select the model from observed behavior and implementation size.

Existing anchors: request streaming tests, steering integration tests,
`PendingInputServer`, ReAct worker tests. These are stronger AI requirements
than the basic core tool-loop example.

### 06 — History, compaction, and restore

Two questions share history. Compaction replaces an old prefix. Restore the
Agent and ask a third question with fresh runtime resources.

- Record exact messages sent after each commit and after restore.
- Preserve tool-call/result pairing, attachments, active skill content, and
  the retained recent suffix.
- Keep another queued request from being lost during compaction.
- Reject process handles and closures from committed state. Rebuild derived
  ReqLLM tools and other runtime resources outside that state.
- Keep the current interrupted-stream failure behavior unless the user chooses
  a new recovery feature. Test standalone token resume separately in `14`.
- State the measured context limit. Message or byte limits do not prove a
  model-specific token limit.

Core sources: `03_02_conversation_history`, `03_08_context_compaction`.

## Acceptance method

For each accepted profile, record:

1. User task, public call, and expected result.
2. Domain state, Plugin state, local Flow state, and transient runtime data.
3. Exact commit boundary and external work that can survive failure.
4. Success, validation failure, provider/tool failure, cancellation, and recovery
   cases that apply to the new behavior.
5. Existing feature tests and core examples that support the case.
6. Status: proposed, implemented and passing, or blocked by a named contract.

Use non-default prior state when checking failure preservation. Record provider
and tool calls; a final answer alone does not prove the requested execution.
Prove concurrency with worker barriers, not elapsed-time guesses. Keep a live
provider suite separate, with explicit cost limits. No live run is part of this
draft.

For Flow adoption, inspect the compiled Flow as well as behavior. A single
opaque Action that wraps the complete old scheduler does not prove use of Map,
Iterate, subflows, or Exec cancellation. Reuse core execution; retain AI policy.
